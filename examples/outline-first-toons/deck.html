1Why asking for slides first goes wrong

  • Claude can now build a deck in any conversation. Getting a deck is easy; getting the deck you want is the hard part.
  • A deck built before the content settles gets rebuilt every time the content changes. Every "redo the deck" pays for the whole deck again.
  • Work from one chat isn't reliably there in the next unless it's saved where Claude reads it.
Remember

Iterate on the outline. Build the deck once.

Myth vs fact

1.1What people believe about AI-made decks

Asking for the whole deck at once is the fastest way.

It's fastest to the first draft. Each later change rebuilds slides that were already fine.

An outline is extra work.

The outline becomes the deck's structure, its speaker notes, and its source list.

1.2The cost of rebuilding

Revising an outline changes a few hundred words. Revising a built deck means regenerating and re-checking slides. Unverified

2.1Phase 1: the outline

  • Claude researches the topic. Your notes are leads, not the limit.
  • Each section becomes a slide: top-level sections run across, subsections go below.
  • Revise by section number ("revise 4.2"). From v0.2 on, numbers don't change.
Tip

Ask Claude to interview you before it drafts anything, a few questions at a time.

Source: Best practices for Claude Code

2.2The approval gate

  • DECISIONS.md is a dated log. Claude's suggestions are Proposed; only the approver makes them Decided.
  • Phase 2 starts only when the log has the approval line.
Watch out

Without a recorded approval, a casual "can I see one slide?" starts the deck early, and the deck drifts from the outline.

2.3Phase 2: the deck

  • Start a fresh chat. Claude builds from the approved outline as written, without new research.
  • First pass: title, agenda, and every top-level slide. Second pass: the detail slides.
  • Later content changes go to the outline first; then only those slides are rebuilt.

3Files, not chat history, carry the work

  • A Claude Project holds instructions and knowledge files that every chat in the project uses. Projects are on every plan, including Free (up to five projects).
  • Three files hold the presentation's state: BRIEF.md (the settings), OUTLINE.md (the content), DECISIONS.md (what was agreed).
  • Claude updates the files at checkpoints: a finished section, a decision, an approval, or the end of a chat. Unverified
Remember

If it isn't in a file, the next chat may not know it.

3.1The three state files

BRIEF.md

"What this talk is"

Topic, audience, date, sources, style. Filled in by an interview in the first chat.

OUTLINE.md

"What it says"

Numbered sections, tags, and the time plan. The source of truth for content.

DECISIONS.md

"What we agreed"

Dated, one line each, only ever added to.

3.3When Claude can't write the files

  • If a chat can't update the files, Claude ends with "Updates for OUTLINE.md" and "Updates for DECISIONS.md", ready to paste, and says the files weren't updated.
  • To recover, ask a new chat to find that message with past-chat search and apply it. Past-chat search needs a paid plan.
Watch out

Check the file after Claude says it updated it. File tools can stop working partway through a chat.

4Tags: say what it is, let the style decide the look

  • Tags mark what a piece of content is: a tip, a warning, a quiz, a hands-on activity, a speaker note.
  • The style guide decides what each tag looks like. Swap the guide and the same outline gets a new look.
  • Callouts use GitHub's alert syntax, so the outline still reads as plain text.
  • Claude adds tags while drafting and tells you which ones; you keep or remove them.

4.1Callouts: five boxes

Tip

A shortcut or better way to do something

Remember

The one thing to keep from this slide

Watch out

A hazard, common mistake, or cost trap

Under the hood

Technical depth that non-technical attendees can skip

Field note

A real example, story, or observed result

  • Syntax: a line > [!TIP], then the text.
Tip

One callout per slide at most. When every slide has one, none of them stand out.

4.2Slide types: quizzes, myths, recaps, activities

  • Quick check: a question; the answer appears on a click.
  • Myth vs fact: common beliefs, each corrected on a click.
  • Recap: three points that close a section.
  • Try it yourself: steps, time needed, and what you should see, so it works without a presenter.

4.4Tag one section

Time: 5 minutes

  1. Pick one part of a talk you're working on.
  2. Write it as ## 1. Title with three main points.
  3. Add one callout: a tip, a warning, or something to remember.
  4. Ask Claude which slide type would suit one detail slide.
You should see a section that already reads like a slide, with one tag the deck can render.

4.5Same outline, a different look

  • Point BRIEF.md at a different style guide and rebuild. The outline doesn't change.
  • Make your own guide from STYLE-GUIDE-TEMPLATE.md, for example in your team's brand.
  • A tag the style guide doesn't know stops the build and gets reported. Nothing is guessed.

6Where it goes wrong

  • Jumping to slides early: the deck drifts from the outline. Keep the gate.
  • Treating your notes as the whole topic: Claude polishes them instead of researching. Say outright that they're leads.
  • Lost work: a chat ends before the files are updated. Write at checkpoints and check the files.
  • Two authors at once: two people editing one outline from separate chats can overwrite each other.
More below!

6.1Lessons from earlier runs

  • Name the presenter. "I am presenting…" makes Claude treat whoever is chatting as the presenter.
  • Keep rules that apply everywhere (such as "no names on slides") in their own section.
  • Every working tag needs a matching rule to remove it, or it leaks onto slides.
Field note

In one earlier run, the attribution rule was silently dropped when a neighboring instruction section was rewritten.

6.2Review in a fresh chat

  • A new chat isn't anchored to the drafting choices, so it catches more gaps.
  • Anthropic recommends the same for code: a second session is the easiest independent reviewer.
