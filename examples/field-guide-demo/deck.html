1Why outline first

  • Text is cheap to write, revise, and re-read. A finished deck is expensive on all three.
  • Every "redo the deck" pays for the whole deck again.
  • Coding agents are advised to work the same way: plan in text, approve, then build.

Remember

Iterate on the outline. Build the deck once.

2Phase 1: the outline

  • Numbered sections map straight to slides: top-level sections are horizontal slides, subsections are vertical ones.
  • Two state files carry progress between chats: OUTLINE.md and DECISIONS.md.
  • Phase 2 starts only when DECISIONS.md records approval.

Tip

2.2The approval gate

  • DECISIONS.md logs dated decisions as Proposed or Decided.
  • The gate line: Decided · Outline v1.0 approved; Phase 2 begins.
Watch out

Without the gate line, a casual "can I see a slide?" starts Phase 2 early and the deck drifts from the outline.

Try it yourself

2.4Tag one section

Time: 5 minutes

  1. Pick a section of a talk you are working on.
  2. Rewrite it as ## N. Title with three main points.
  3. Add one callout where it fits: a tip, a warning, or something to remember.
  4. Ask Claude which slide type would suit one of the subsections.
You should see a section that already reads like a horizontal slide, with one tag you could render.

3Style tags

  • Tags say what a piece of content is: a tip, a hazard, a quiz. The style guide decides how each one looks.
  • Callouts use GitHub's alert syntax, so outlines stay readable as plain Markdown.
  • Swap the style guide and the same outline renders in a different theme.
Source: GitHub: alerts

3.1Callout syntax

> [!WATCHOUT] Don't skip the gate
> Phase 2 starts only after the approval is recorded.
  • The type goes on its own line; every line starts with >.
  • Text after the type is an optional title.
Under the hood

GitHub renders five alert types natively (as of November 2, 2026). Custom types such as FIELDNOTE show on GitHub as an ordinary quote; the deck build is what gives them their look.
